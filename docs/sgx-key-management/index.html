SGX Hardware Architecture & Rust Toolchain

Building an Intel SGX enclave in pure Rust with Fortanix EDP

A technical guide to compiling, running, and managing key material inside Intel SGX Enclave Page Cache (EPC) memory using pure Rust.

traces-sm is an open-source key and secret management framework that runs its cryptographic operations inside an Intel SGX enclave, written entirely in Rust on Fortanix EDP.

1. Why Fortanix EDP (`x86_64-fortanix-unknown-sgx`)?

Traditionally, developing applications for Intel SGX required the official C/C++ Intel SGX SDK or wrapper toolchains like Teaclave / Baidu SGX SDK. These SDKs present several drawbacks for memory-safe key management: C-style memory bugs (buffer overflows, use-after-free) can break the security guarantees of the enclave itself, and interfacing Rust code with C SDKs requires extensive unsafe FFI bindings.

Fortanix EDP (Enclave Development Platform) integrates Intel SGX support directly into the official Rust compiler standard library as a Tier-2 target: x86_64-fortanix-unknown-sgx. This enables compiling pure Rust code into SGX enclave binaries without C toolchain dependencies or C-based runtime glue.

Inside traces-sm, the enclave crate (enclave/) is built against Fortanix EDP. Memory allocations use standard Rust collections (Vec, HashMap), and panics abort execution immediately to prevent enclave state corruption.

2. Cargo Configuration for Enclave Compilation

Building the enclave requires target setup in .cargo/config.toml and manifest declarations in enclave/Cargo.toml. Below is the configuration structure used in traces-sm: 

# enclave/Cargo.toml
[package]
name = "traces-sm-enclave"
version = "0.1.0"
edition = "2021"

[[bin]]
name = "traces-sm-enclave"
path = "src/main.rs"

[dependencies]
sgx-isa    = { version = "0.4", optional = true }  # Real EGETKEY HW execution
ring       = "0.17"                                # AES-GCM & HKDF primitives
rsa        = { version = "0.9", features = ["sha2", "pem"] }
zeroize    = { version = "1", features = ["derive"] }

[features]
default = []
sgx-hw  = ["sgx-isa"]

[profile.release]
opt-level = 3
lto       = "thin"
panic     = "abort"
strip     = "debuginfo"

3. In-Enclave Key Sealing (`enclave/src/sealing.rs`)

When secrets must be written to disk, they cannot be stored in plaintext. Intel SGX provides the hardware instruction EGETKEY, which derives a hardware root key unique to the specific CPU and enclave measurement (MRENCLAVE or MRSIGNER).

In enclave/src/sealing.rs, traces-sm derives a Master Sealing Key using EGETKEY, expands it with HKDF-SHA256, and encrypts payloads with AES-256-GCM. Below is a simplified representation of the sealing flow: 

// Data sealing architecture in enclave/src/sealing.rs
pub fn seal(plaintext: &[u8], purpose: &str) -> Result<Vec<u8>, EnclaveError> {
    // 1. Issue EGETKEY with KEYPOLICY_MRSIGNER to fetch 128-bit hardware key
    let raw_hw_key = get_sgx_hardware_key(KEYPOLICY_MRSIGNER)?;

    // 2. Expand raw key with HKDF-SHA256 and purpose label ("seal:secrets")
    let master_key = hkdf_expand(&raw_hw_key, b"traces-sm-enclave-v1", purpose)?;

    // 3. Encrypt payload with random 12-byte nonce & AES-256-GCM
    let nonce = generate_random_nonce()?;
    let ciphertext = aes_gcm_encrypt(&master_key, &nonce, plaintext)?;

    // 4. Format sealed blob: [ Nonce (12B) || Ciphertext || Tag (16B) ]
    Ok(format_sealed_blob(&nonce, &ciphertext))
}

Because the sealing key is derived directly from CPU silicon registers via EGETKEY, sealed blobs written to disk cannot be decrypted on any other physical CPU or outside an enclave bearing the matching measurement.

4. Memory Isolation & Volatile Zeroization

Inside SGX Enclave Page Cache (EPC), memory pages are encrypted by hardware. However, when private keys are dropped, standard deallocators do not overwrite memory buffers. In high-assurance key management, memory registers must be sanitized immediately upon destruction.

All private key byte vectors inside traces-sm wrap in zeroize::Zeroizing<T>. Read our detailed guide on how traces-sm zeroizes secrets in Rust to understand how volatile writes and compiler memory fences prevent LLVM dead-store optimization risks.
