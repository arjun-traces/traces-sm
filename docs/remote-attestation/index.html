Intel DCAP Attestation & Network Trust Architecture

Remote attestation and RA-TLS in traces-sm

Establishing cryptographic proof of enclave identity, code measurement, and hardware authenticity over untrusted networks.

traces-sm is an open-source key and secret management framework that runs its cryptographic operations inside an Intel SGX enclave, written entirely in Rust on Fortanix EDP.

1. What Is Intel SGX Remote Attestation?

When a client or peer node communicates with a secret manager over a network, traditional TLS only proves that the server possesses a domain certificate. It provides no guarantee that the server binary is running inside a secure hardware enclave or that the code has not been tampered with by a malicious host administrator.

**Remote Attestation (RA)** solves this problem by allowing an Intel SGX enclave to generate a hardware-signed proof (an **Attestation Quote**) verified by Intel's ECDSA Quoting Enclave. The quote contains two fundamental cryptographic identity hashes:

  • MRENCLAVE (Enclave Measurement Hash): A 256-bit SHA-256 digest representing the exact initial code, data, and layout of the enclave binary loaded into Enclave Page Cache (EPC) memory. Any modification to a single byte of enclave code changes MRENCLAVE.
  • MRSIGNER (Signer Measurement Hash): A 256-bit hash of the authority key that signed the enclave binary, representing the vendor responsible for building the enclave.

2. Remote Attestation TLS (RA-TLS) Handshake

Instead of performing out-of-band attestation verification before establishing network connections, **RA-TLS** embeds the Intel DCAP attestation quote directly inside X.509 TLS certificate extensions (OID 1.3.6.1.4.1.311.21.10). During the TLS handshake, peer nodes extract and verify the attestation quote before completing session key agreement. 

Node A (SGX Enclave Primary)                        Node B (Peer Client / Enclave)
  │                                                      │
  ├────── ClientHello + RA-TLS Cert (DCAP Quote A) ─────>│
  │                                                      │
  │<───── ServerHello + RA-TLS Cert (DCAP Quote B) ──────┤
  │                                                      │
  │ [ Verify Quote B via Intel PCCS ]                    │ [ Verify Quote A via Intel PCCS ]
  │ [ Validate MRENCLAVE & MRSIGNER ]                    │ [ Validate MRENCLAVE & MRSIGNER ]
  │                                                      │
  └══════════════ Encrypted mTLS Session Established (AES-256-GCM) ══════════════┘

In traces-sm, certificate generation and mTLS networking are handled using rcgen (version 0.13) and rustls (version 0.23) inside the enclave crate (enclave/Cargo.toml).

4. Why RA-TLS Outperforms Host Authentication

Unlike traditional secret management architectures where API proxies authenticate using domain certificates issued to host servers (compare with HashiCorp Vault), RA-TLS ensures that:

  1. Clients know they are communicating with genuine Intel SGX hardware.
  2. Clients verify that the enclave code matches the exact open-source build (MRENCLAVE).
  3. Plaintext secret payloads transmitted over mTLS are decrypted exclusively inside hardware-protected Enclave Page Cache memory (read our pure Rust SGX enclave guide).

5. Frequently Asked Questions

How does Remote Attestation (RA-TLS) work in traces-sm?

traces-sm uses Remote Attestation TLS (RA-TLS) to embed Intel DCAP quotes directly into X.509 TLS certificate extensions. Peer nodes verify the enclave's measurement hash (MRENCLAVE) and signer hash (MRSIGNER) against Intel PCCS before establishing mTLS channels.
